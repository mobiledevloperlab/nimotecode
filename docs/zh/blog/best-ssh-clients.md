# 如何评估移动 IDE：工作流、执行环境与审查

选择移动 IDE，应从任务开始，而不是从功能数量开始。查看服务状态可能只需要终端；修复一个问题则可能还需要文件浏览器、编辑器、测试与可读的 diff。关键在于这些步骤能否在你的设备上顺畅衔接。

本文由 NimoteCode 团队撰写，解释我们的评估标准与产品定位，不是独立排名，也不是产品间的性能实测。

## 先确定执行环境

比较界面之前，先决定项目能在哪里运行。检查操作系统、CPU 架构、依赖与可用资源。能够在手机上编辑仓库，不代表手机能运行项目工具链。

| 方案 | 适合从这里开始的情况 | 需要验证的环节 |
| --- | --- | --- |
| SSH 终端 | 你已经习惯在主机上使用命令行工具 | 密钥处理、重连与终端操作体验 |
| 浏览器 IDE | 已有托管或自托管开发环境 | 触控输入、屏幕布局、网络与服务限制 |
| 本地编辑器或工作区 | 任务能由设备支持的工具完成 | 文件访问、执行能力与资源占用 |
| 集成式移动工作区 | 需要频繁切换文件、命令与审查 | 各视图是否使用同一项目、分支与工作目录 |

这些方案并非互斥。终端可以运行编辑器与 Git，浏览器 IDE 也可以提供完整工作流。只有实际降低任务中的操作成本，集成才有价值。

## 用一个小任务进行可重复的评估

在熟悉的仓库中使用临时分支。记录应用版本、设备、项目与网络条件，让后续比较有依据。

1. 打开项目，确认根目录、分支与执行环境。
2. 修改一个小文件并保存，确认运行环境能看到已保存内容。
3. 运行项目的常规检查，确认输出与退出状态清晰可读。
4. 审查 diff，包括意外修改的文件；检查长行与删除内容是否容易阅读。
5. 断开连接并重连，确认分支、路径与已保存状态，再继续操作。

失败的步骤比长长的功能表更有参考价值。例如重连后丢失工作目录，即使 SSH 本身正常，下一条命令仍可能作用于错误项目。

## 单独评估 AI

AI 是可选能力，不是 IDE 的必要条件。如果使用 AI，应检查审批设置、可访问文件、命令权限与数据路径。代码存储在自己的主机上，仍可能被发送给外部模型服务商。

给 Agent 一个范围明确、验证方式清楚的任务。审查最终 diff 和实际命令输出；自信的完成消息不能代替验证。审批行为可能取决于模式与配置，应实际测试，而不是假定每个动作都会弹出确认。

## NimoteCode 的定位

NimoteCode 将项目浏览、编辑、终端访问、Git 审查与 AI 放在移动工作区中。SSH 工作区使用主机工具链；受支持的 Android 设备也可以使用独立的 Local Linux 环境，该环境不适用于 iOS。

## 根据实际结果做选择

选择能可靠完成任务的最简单方案。如果现有终端工作流已经顺手，就继续使用。当文件、命令与审查之间的切换成为瓶颈时，再考虑集成式工作区。对于较大的改动，应先判断屏幕是否仍能支持仔细审查，再决定是否在移动端完成。

当前产品与平台入口见[下载页](/zh/download)。最有价值的试用，是在自己的仓库中完成一次经过审查的改动。
