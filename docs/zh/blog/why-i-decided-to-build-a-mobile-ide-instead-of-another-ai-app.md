# 为什么我选择做一款移动 IDE，而不是另一个 AI App

我曾从事底层系统开发，经常只负责大型产品中的一小部分。我想构建一个自己能够理解并持续改进完整工作流的产品。这种愿望，加上对 AI 辅助编程的尝试，让我开始考虑移动 IDE。

吸引我的不只是生成更多代码，而是缩短“提出改动”与“得到可检查结果”之间的距离。有用的回答最终仍须进入正确文件，在正确环境中运行，并接受审查。

## 我想解决的交接问题

在我使用过的聊天式工作流中，信息依靠手动搬运：把文件贴进对话，将建议复制回编辑器，到另一个地方运行命令，再把错误带回对话。每次交接都可能丢失路径、依赖或当前状态中的重要信息。

工作区可以把这些步骤连接起来。这不会让模型永不出错，但能让模型输入与操作更容易对应到项目。这个设计判断来自个人经历，不是对所有 AI 应用的市场调查。

## 用一个小任务说明

以修正文档中的配置选项为例。用户说明预期行为，Agent 查找相关文档与实现，提出范围明确的修改，并运行相应检查。随后用户阅读 diff，决定是否提交。

如果 Agent 修改无关文件、隐藏失败命令或丢失当前分支，任务就失败了。漂亮的回答无法弥补这些问题。因此，界面需要像呈现对话一样，清晰地呈现路径、变更文件和验证输出。

## 手机带来的变化

离开工位时，手机便于接手任务，但较小的屏幕也让对比与审查更困难。简短的自然语言指令可以减少输入，不能取消结果检查。大型重构仍可能更适合大屏幕。

我的设计目标是让用户恢复一个范围明确的任务，而不必在多个应用间重新拼凑上下文。文件、命令、Git 状态与 AI 活动应指向同一个工作区。对我来说，这比单独丰富聊天界面更有价值。

## 分清三种职责

| 职责 | 需要明确的信息 |
| --- | --- |
| 意图 | 目标、范围与验收标准 |
| 操作 | 涉及的文件和命令，以及对应权限 |
| 审查 | 实际改动、检查结果与未解决问题 |

Agent 可以协助三个环节，但应用不应隐藏它们的边界。尤其需要明确：允许编辑，不自动等于允许发布或部署。

## 如何判断产品是否有用

如果用户能完成一次聚焦的改动、理解发生了什么，并在失败后恢复工作，产品才体现出价值。这比生成代码行数或对话长度更有参考意义。
